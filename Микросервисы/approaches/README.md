# Домашнее задание "Микросервисы: подходы" - `Прыкин Сергей`

## Контекст
Крупная компания, микросервисная архитектура, множество команд разработки. Требуется единая платформа для CI/CD, централизованного логирования и мониторинга. Критерии выбора: зрелость, вендорская поддержка, low barrier to entry для разработчиков, бесшовная интеграция компонентов.

## Задача 1: CI/CD платформа

### Требования
- Облачная система, интеграция с Git.
- Репозиторий на каждый сервис.
- Запуск сборок по триггеру из Git и по кнопке с параметрами.
- Шаблоны сборок, несколько конфигураций из одного репозитория.
- Кастомные шаги, свои Docker-образы для раннеров.
- Собственные агенты на своих серверах.
- Параллельный запуск сборок и тестов.
- Безопасное хранение секретов.

### Сравнительная таблица

| Критерий | **GitLab CI/CD** | **GitHub Actions** | **Jenkins** |
| :--- | :--- | :--- | :--- |
| **Облачность** | Да (SaaS или Self-Hosted). | Да (SaaS, Enterprise Server). | Да (только Self-Hosted или облачные VM). |
| **Git-репозитории** | Встроенный GitLab (репо на сервис). | Встроенный GitHub (репо на сервис). | Подключается к любому Git. |
| **Триггеры сборок** | Push, MR, Tag, API, Webhook, Schedules. | Push, PR, Tag, Workflow Dispatch (кнопка с параметрами). | Webhook, Polling SCM, ручной запуск. |
| **Запуск с параметрами** | Да (Manual Job с variables, Pipeline Schedules). | Да (Workflow Dispatch с inputs). | Да (Build with Parameters, классика). |
| **Шаблоны сборок** | Да (Pipeline Templates, CI/CD Catalog, Includes). | Да (Reusable Workflows, Starter Workflows). | Да (Shared Libraries, Job DSL). |
| **Несколько конфигураций** | Да (Child Pipelines, Matrix Jobs). | Да (Matrix Strategy). | Да (Matrix Plugin, Multi-branch). |
| **Кастомные шаги** | Да (Bash, Scripts, любые Docker-образы). | Да (Actions + Bash). | Да (любые плагины + Bash). |
| **Свои Docker-образы** | Да (image: в .gitlab-ci.yml). | Да (container: в workflow). | Да (плагины Docker/Kubernetes). |
| **Свои агенты (раннеры)** | Да (GitLab Runner, любой сервер, K8s). | Да (Self-hosted Runners). | Да (агенты — основа Jenkins). |
| **Параллельные сборки** | Да (Parallel Jobs, Needs). | Да (Concurrency Groups). | Да (Executors, Agents). |
| **Параллельные тесты** | Да (Parallel:matrix + Reports). | Да (Matrix + Sharding). | Да (Splitting Tests). |
| **Хранение секретов** | Да (CI/CD Variables, Vault Integration). | Да (Secrets, Environments). | Да (Credentials Store, Vault Plugin). |
| **Главный плюс** | **All-in-one: Git, CI/CD, Registry, Security. Бесшовно.** | Экосистема GitHub, 20 000+ Actions. | Гибкость, десятки тысяч плагинов. |
| **Главный минус** | SaaS-версия может быть дорогой для 1000+ разработчиков. | Локаут в GitHub, сложнее self-hosted. | Адский техдолг, плагины ломают друг друга, устарел морально. |

### Выбор: GitLab CI/CD

**Обоснование для крупной компании:**

1.  **Единая платформа.** В одном месте живут: исходный код, ревью кода, CI/CD, Container Registry, Wiki, Vulnerability Scanning. Разработчику не надо прыгать между GitHub, Jenkins и Artifactory — всё в одном окне браузера. Это снижает когнитивную нагрузку и количество интеграционных точек, которые могут сломаться.

2.  **Репозиторий на каждый сервис.** GitLab из коробки позволяет создать Group (команда) и внутри неё Project (сервис). Политики доступа наследуются, настройка CI/CD — через единый механизм.

3.  **Запуск по кнопке с параметрами.** Ручной запуск пайплайна (Manual Job) с возможностью передать переменные прямо из UI. Плюс Pipeline Schedules для ночных сборок. GitHub Actions тоже так умеет, но в GitLab это сделано прозрачнее для сложных сценариев типа "собрать ветку, но с версией X и деплоить в окружение Y".

4.  **Шаблоны и Includes.** В крупной компании 200+ сервисов. Писать для каждого .gitlab-ci.yml с нуля — безумие. GitLab позволяет вынести общую логику в центральный репозиторий шаблонов и подключать через include. Поменяли шаблон в одном месте — подхватили все сервисы. CI/CD Catalog делает это ещё удобнее.

5.  **Свои раннеры на своих серверах.** GitLab Runner ставится на bare metal, VM, в Kubernetes — куда угодно. Команды могут иметь свои выделенные раннеры с GPU или доступом к специфичным сетям. GitHub Actions self-hosted runners тоже так умеют, но GitLab Runner более зрелый и гибкий в настройке.

6.  **Почему не Jenkins?** Jenkins — это прошлое. Чтобы он делал то, что GitLab из коробки, нужно поставить 30 плагинов, написать 500 строк Groovy и молиться, чтобы плагины не конфликтовали при обновлении. Jenkins не умер, но для нового проекта в крупной компании его выбирать — это как строить новый дата-центр на ленточных библиотеках. Можно, но зачем?

7.  **Почему не GitHub Actions?** GitHub Actions прекрасен, если вы уже в экосистеме GitHub. Но в крупной компании часто нужно self-hosted решение (закрытый контур, compliance). GitHub Enterprise Server существует, но он дорог, а GitLab Self-Hosted — зрелый и проверенный. Плюс GitLab даёт встроенный Container Registry и Security Scanning без сторонних костылей.

## Задача 2: Централизованное логирование

### Требования
- Сбор логов со всех хостов.
- Минимальные требования к приложениям (stdout).
- Гарантированная доставка.
- Поиск, фильтрация, пользовательский UI.
- Доступ для разработчиков.
- Shareable ссылки на сохранённый поиск.

### Сравнительная таблица

| Критерий | **ELK Stack (Elasticsearch + Logstash + Kibana)** | **Grafana Loki + Promtail** | **OpenSearch** |
| :--- | :--- | :--- | :--- |
| **Сбор логов** | Агенты (Filebeat) или прямая отправка в Logstash. | Promtail (агент), легче Filebeat. | Агенты (Data Prepper, Fluentd, Filebeat). |
| **Stdout-логи** | Да, Filebeat читает Docker/K8s stdout. | Да, Promtail изначально под это заточен. | Да, аналогично Filebeat. |
| **Гарантированная доставка** | Да (persistent queues в Logstash/Filebeat). | Да (Promtail пишет позиции, не теряет при рестарте). | Да (persistent queues в Data Prepper). |
| **Поиск и фильтрация** | **Мощнейший полнотекстовый поиск (Lucene).** | LogQL — простой, но слабее Lucene. | Полнотекстовый поиск (форк Elasticsearch). |
| **UI для разработчиков** | Kibana — зрелый, ролевая модель, spaces. | Grafana — единый UI для логов и метрик. | OpenSearch Dashboards (форк Kibana). |
| **Shareable ссылки** | Да (сохранённый поиск = ссылка). | Да (Explore URL). | Да (аналогично Kibana). |
| **Главный плюс** | **Самый мощный поиск, десятки интеграций.** | Легче, дешевле, единый UI с мониторингом. | Полностью открытый код (нет проблем с лицензией). |
| **Главный минус** | Тяжёлый, требователен к ресурсам. Elasticsearch — прожорливый Java-процесс. | Нет полнотекстового поиска уровня Lucene. | Догоняет ELK по экосистеме, сообщество меньше. |

### Выбор: Grafana Loki + Promtail

**Обоснование для крупной компании:**

1.  **Минимальные требования к приложению.** Всё, что нужно от разработчика — писать логи в stdout/stderr. Никаких спецбиблиотек, форматтеров, TCP-сокетов. Promtail сам подхватит логи из Docker-контейнеров или файлов на хосте. В K8s это вообще одна DaemonSet-команда.

2.  **Лёгкость и стоимость.** Elasticsearch — это JVM, heap, GC pauses, настройка шардов. Loki индексирует только метаданные (лейблы), а сами логи хранит в object storage (S3, MinIO). Это в разы дешевле и быстрее по ingestion, чем ELK. Для крупной компании с терабайтами логов в день это миллионы рублей экономии на железе.

3.  **Гарантированная доставка.** Promtail хранит курсор (позицию в файле, с которой он читает). Если агент упал, он поднимется и продолжит с того же места. Loki сам по себе stateless, надёжность хранилища обеспечивает S3/MinIO.

4.  **Единый UI с мониторингом.** В крупной компании разработчики и так сидят в Grafana для метрик. Добавляем вкладку Explore, переключаем data source на Loki — и вот они уже ищут логи в том же интерфейсе. Не нужно учить вторую систему. Kibana — отличный инструмент, но это отдельный интерфейс, отдельные роли, отдельная поддержка.

5.  **Shareable ссылки.** В Grafana Explore URL кодирует запрос, временной диапазон и data source. Разработчик нашёл ошибку, скопировал ссылку, кинул в чат коллеге — тот открыл и видит то же самое. Работает без танцев с бубном.

6.  **Почему не ELK?** ELK — это комбайн, который умеет всё. Но для логов из stdout в 90% случаев его мощь избыточна, а счёт за ресурсы — неоправдан. Elasticsearch нужен, когда у вас сложные аналитические запросы к логам. Для "найти ошибку по trace_id" Loki справляется на отлично.

7.  **Почему не OpenSearch?** OpenSearch — прямой наследник Elasticsearch после смены лицензии. Если бы компания уже сидела на ELK и мигрировала — да. Но для нового стека Loki легче, дешевле и интегрирован в Grafana, которая уже выбрана под мониторинг.

## Задача 3: Мониторинг

### Требования
- Сбор метрик со всех хостов (CPU, RAM, HDD, Network).
- Сбор метрик по каждому сервису.
- Специфичные для сервиса метрики.
- UI с запросами и агрегацией.
- Настраиваемые дашборды.

### Сравнительная таблица

| Критерий | **Prometheus + Grafana** | **VictoriaMetrics** | **Datadog** |
| :--- | :--- | :--- | :--- |
| **Сбор метрик с хостов** | Node Exporter (де-факто стандарт). | Совместим с Prometheus exporters. | Встроенный агент. |
| **Сбор метрик сервисов** | Prometheus exporters (тысячи готовых). | Те же exporters, Prometheus-compatible API. | Агент + APM. |
| **Кастомные метрики** | Да (Prometheus client libraries). | Да (те же библиотеки). | Да (DogStatsD, APM). |
| **Масштабируемость** | Thanos/Cortex для долгого хранения и HA. | Встроенная кластеризация, эффективнее Prometheus. | SaaS, масштабирует вендор. |
| **UI и запросы** | Grafana + PromQL (мощный, но требует изучения). | Grafana + MetricsQL (совместим с PromQL). | Встроенный UI, проприетарный язык. |
| **Дашборды** | Grafana Dashboards (JSON, GitOps, тысячи готовых). | Grafana Dashboards. | Встроенные дашборды. |
| **Стоимость** | Бесплатно (Open Source). | Бесплатно (Open Source), дешевле в эксплуатации. | Очень дорого при объёмах крупной компании. |
| **Главный плюс** | **Стандарт индустрии. Любой exporter уже существует.** | Совместимость с Prometheus, но быстрее и легче по ресурсам. | SaaS — ноль усилий на эксплуатацию. |

### Выбор: Prometheus + Thanos + Grafana

**Обоснование для крупной компании:**

1.  **Стандарт индустрии.** Prometheus — это то, на чём строят мониторинг все, кто не хочет платить Datadog $100k/месяц. Node Exporter для хостов, Service Exporter для БД и брокеров, Blackbox Exporter для внешних проверок. Любой микросервис отдаёт метрики в формате Prometheus. Экосистема настолько большая, что ты не пишешь exporters — ты их скачиваешь готовыми.

2.  **Сбор метрик по хостам и сервисам.** Один DaemonSet с Node Exporter закрывает все хосты (CPU, RAM, диск, сеть, даже температуру процессора). Для каждого микросервиса — аннотации в pod'ах, Prometheus сам их найдёт и начнёт скрейпить. Никаких агентов, которые надо прописывать в коде.

3.  **Специфичные метрики.** Разработчик добавляет Prometheus-клиент в своём языке (Java, Go, Python — библиотеки есть под всё) и отдаёт бизнес-метрики: количество заказов, latency эндпоинтов, ошибки бизнес-логики. Prometheus их подхватит автоматически.

4.  **PromQL и Grafana.** PromQL — мощный язык запросов. `rate(http_requests_total[5m])` — и ты видишь RPS. `histogram_quantile(0.99, ...)` — и ты видишь 99-й перцентиль latency. Grafana визуализирует это в дашборды, которые хранятся в Git (Infrastructure as Code). Поменял дашборд в репозитории — CI/CD задеплоил в Grafana.

5.  **Thanos для крупной компании.** Один Prometheus не вывозит долгое хранение и HA на масштабах enterprise. Thanos добавляет: глобальный view на все кластеры Prometheus, downsampling для снижения нагрузки на диск, object storage как долговременное хранилище метрик. Prometheus падает? Thanos Query идёт в object storage и отдаёт данные. Никакой потери метрик.

6.  **Почему не VictoriaMetrics?** VictoriaMetrics — отличный продукт, реально быстрее и легче Thanos по ресурсам. Но Thanos — это модульная экосистема (Sidecar, Query, Store, Compactor), которую можно размазать по разным командам и кластерам. В крупной компании с зоопарком инфраструктуры эта модульность и десятки интеграций перевешивают сырую производительность.

7.  **Почему не Datadog?** Datadog прекрасен, когда у тебя 20 серверов и нет своей DevOps-команды. В крупной компании с тысячами хостов счёт от Datadog превысит зарплату команды SRE, которая построит Prometheus+Grafana и будет их обслуживать. Контроль над данными (on-premise MinIO для метрик) — тоже аргумент для compliance.

## Итоговый стек платформы

| Задача | Выбор | Ключевой аргумент |
| :--- | :--- | :--- |
| CI/CD | **GitLab CI/CD** | All-in-one платформа (Git, CI/CD, Registry, Security), шаблоны через includes, свои раннеры. |
| Логирование | **Grafana Loki + Promtail** | Лёгкий, дешёвый (S3/MinIO), единый UI с Grafana, stdout из коробки. |
| Мониторинг | **Prometheus + Thanos + Grafana** | Стандарт индустрии, тысячи exporters, Thanos для HA и долгого хранения, Grafana дашборды как код. |

**Взаимодействие компонентов:**
- Разработчик пушит код в GitLab → GitLab Runner собирает Docker-образ → пушит в GitLab Container Registry.
- Сервис деплоится в Kubernetes → пишет логи в stdout → Promtail собирает → отправляет в Loki.
- Сервис отдаёт метрики на /metrics → Prometheus скрейпит → Thanos хранит долгосрочно → Grafana отображает и логи (Loki), и метрики (Prometheus) в одном интерфейсе.
