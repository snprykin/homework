## Задача 1: API Gateway

### Требования
- Маршрутизация входящих запросов на микросервисы.
- Централизованная проверка аутентификации.
- Терминация HTTPS.

### Сравнительная таблица

| Критерий | **Kong Gateway** | **Apache APISIX** | **Envoy (c контроллером)** |
| :--- | :--- | :--- | :--- |
| **Маршрутизация** | Динамическая, без даунтайма. | Динамическая, без даунтайма. | Динамическая через xDS, нативный Gateway API K8s. |
| **Аутентификация** | Много готовых плагинов (OIDC, JWT, LDAP, Keycloak). | Много плагинов, догоняет Kong по количеству. | Через внешний фильтр (ext_authz). Требует отдельный сервис. |
| **Терминация HTTPS** | Да, на базе OpenResty/Nginx. | Да, на базе OpenResty/Nginx. | Да, встроено. |
| **Enterprise-фичи** | RBAC, Audit Logs, Admin GUI, Workspaces, SSO. | Есть RBAC, но GUI и аудит слабее. | Зависит от контроллера (Istio, Gloo, Contour). |
| **Экосистема и поддержка** | Огромная, плагины под всё. Есть платная Enterprise-версия с вендорской поддержкой. | Растёт быстро, но вендорская поддержка пока скромнее. | Стандарт де-факто в K8s. Вендорская поддержка через сервис-меши. |
| **Сложность для команды** | Низкая. Понятный декларативный конфиг (deck), GUI. | Низкая. Хороший GUI, CRD для K8s. | Высокая. Требует глубокой экспертизы в Envoy-фильтрах. |

### Выбор: Kong Gateway

**Обоснование для крупной компании:**

1.  **Enterprise-ready из коробки.** В Kong есть встроенные RBAC (кто может менять роуты), Audit Logs (кто что поменял и когда) и Workspaces (разделение на команды). Когда 20 команд долбятся в один шлюз, это не фича, а необходимость. У APISIX это есть, но сырее. У Envoy — только на уровне сервис-меша с доп. настройками.

2.  **Готовые плагины под корпоративный SSO.** Крупная компания = LDAP или OIDC (Keycloak, Okta, Azure AD). У Kong плагины под это отточены годами. Не нужно писать микросервис для ext_authz, как в Envoy. Включил плагин OIDC, прописал URL провайдера — работает.

3.  **Зрелость и поддержка.** Kong с 2015 года в продакшене у тысяч компаний. Есть платная подписка с 24/7 поддержкой, что важно, когда шлюз упал в 3 часа ночи, а бизнес стоит. APISIX — отличный проект, но вендорская поддержка пока слабее, а консервативный энтерпрайз этого не любит.

4.  **Декларативный подход.** Конфиг в Git (decK), CI/CD прогоняет — шлюз обновлён. Никакой магии, никаких ручных правок в продакшене. Полный аудит изменений.

5.  **Почему не Envoy?** Envoy — это лего. Ты собираешь шлюз сам из фильтров. В крупной компании с 50+ командами это означает, что каждая команда соберёт свой велосипед. Нам нужен стандарт, а не конструктор.

## Задача 2: Брокер сообщений

### Требования
- Кластеризация для надёжности.
- Хранение сообщений на диске.
- Высокая скорость.
- Разные форматы сообщений.
- Гранулярные права доступа (ACL).
- Простота эксплуатации (насколько возможно в энтерпрайзе).

### Сравнительная таблица

| Критерий | **Apache Kafka** | **RabbitMQ** | **Redpanda** |
| :--- | :--- | :--- | :--- |
| **Кластеризация** | Эталон. KRaft-режим стабилен, ZooKeeper убран. | Стабильна. Quorum Queues на RAFT. | Совместима с Kafka API, свой RAFT-движок. |
| **Хранение на диске** | Да, распределённый лог. | Да, для персистентных сообщений и Lazy Queues. | Да, своя файловая система (быстрее Kafka). |
| **Скорость** | Высокая пропускная способность. | Высокая на единичные сообщения (низкая latency). | Быстрее Kafka по latency и пропускной способности. |
| **Форматы** | Любые байты. Схемы через Schema Registry. | Любые байты. | Любые байты. Совместимость со Schema Registry. |
| **Права доступа (ACL)** | Мощные (SASL, ACL на топики/группы). Сложные. | **Удобные (пользователи, vhost, права read/write/configure).** | Kafka-совместимые ACL. |
| **Enterprise-фичи** | Schema Registry, Kafka Connect, ksqlDB, Tiered Storage. | Management UI, Federation, Shovel. | Встроенный Schema Registry, Tiered Storage, Web UI. |
| **Эксплуатация** | Сложная. Тюнинг JVM, партиций, репликации. | **Средняя. Понятный UI, меньше тюнинга.** | Легче Kafka (нет JVM, бинарник на C++), но моложе. |

### Выбор: Apache Kafka

**Обоснование для крупной компании:**

1.  **Стандарт индустрии.** Kafka — это не просто брокер, это платформа для потоков данных. В крупной компании к брокеру подключаются не только микросервисы, но и аналитика, DWH, логи. Kafka Connect позволяет всасывать данные из СУБД без единой строчки кода. RabbitMQ так не умеет — это чистый брокер, а не интеграционная шина.

2.  **Гарантированная надёжность.** ISR-репликация, retention на диске, exactly-once семантика на текущее время уже зрелая. Сообщение не пропадёт, пока не прочитано, и будет храниться столько, сколько сказано в политике. В RabbitMQ очередь может разрастись и уронить ноду.

3.  **Масштабирование.** Партиционирование топиков позволяет размазать нагрузку на десятки брокеров. RabbitMQ тоже можно кластеризовать, но при росте очередей начинаются проблемы с сетевыми перегородками, которые лечатся костылями. Kafka изначально спроектирована для распределённой работы.

4.  **Экосистема.** Schema Registry (Avro/Protobuf) гарантирует, что сервис А не сломает сервис Б кривой JSON-схемой. Kafka Streams/ksqlDB позволяют обрабатывать потоки в реальном времени. Всё это — части одного конструктора, который уже стал стандартом в энтерпрайзе.

5.  **Простота эксплуатации (относительная).** Да, Kafka сложнее RabbitMQ в первоначальной настройке. Но в крупной компании есть выделенная команда платформы. Один раз настроил KRaft-кластер, Ansible-плейбуки, мониторинг в Prometheus — и отдал командам топики через self-service портал. На сегодняшний день KRaft избавили от ZooKeeper, Tiered Storage позволяет не раздувать диски — жить стало легче.

6.  **Почему не Redpanda?** Redpanda — отличный продукт, совместимый с Kafka API, быстрее и без JVM. Но сейчас она всё ещё догоняет по enterprise-фичам (Connect-коннекторы, зрелость Tiered Storage, вендорская поддержка уровня Confluent). Для стартапа — да, для крупной компании, которой нужна гарантированная поддержка 24/7 и 100500 коннекторов — пока Kafka/Confluent вне конкуренции.
